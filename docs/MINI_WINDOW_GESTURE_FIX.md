# 260008：应用上滑拖入小窗时原厂跟手动画被覆盖

显示版本保持 `26.9.260.908.2609081608`，内部版本为 `260008`，保留 `260007` 卡片命中修复及 `260006` 横屏入场修复。固定验收基线仍为 `260005`。

## 录屏与代码证据

2026-09-25 用户提供的应用上滑拖入小窗录屏中，约 1.4–2.8 秒和 4.0–4.4 秒，小窗触发区域已高亮，手指继续移动，应用画面仍停在居中的大卡片位置。约 4.45 秒松手后才出现缩入右上角的过渡。因此不能把问题写成“小窗功能完全失效”或“所有动画均被移除”。

本轮从工程 `original.apk` 解码对照原厂 `AbsSwipeUpHandler`、`LauncherSwipeHandlerV2`、`SwipeUpAnimationLogic` 和 `TaskViewSimulator`。小窗判断、原厂动画路径仍保留，`LauncherSwipeHandlerV2` 与 `SwipeUpAnimationLogic` 的指令内容与原厂一致。冲突在辅助层：`normalizeLiveEntryMatrix()`、`normalizeLiveAppliedScale()` 和 `normalizeLiveEntryScroll()` 除了检查明确的最近任务目标，还允许 `overviewEntryPending` 触发实时画面修正。

这个待入场状态可以在手势仍拖动时存在，不能证明最终目的地是最近任务。它让小窗拖动的原厂矩阵被重新居中、横向滚动被置零、缩放受到卡片下限约束。原厂小窗慢速松手的结束目标是 `HOME`；即使目标回调清掉 `liveSimulatorOverviewTarget`，旧待入场分支仍可能继续影响交接。

## 修正边界

三处实时画面修正现在只在 `setLiveOverviewTarget()` 明确收到 `RECENTS` 目标且使用堆叠样式时生效。手指拖动中的矩阵、滚动和缩放原值直接保留，非最近任务目标关闭修正。没有新增小窗动画、计时延迟或额外手势状态，也没有更改原厂小窗触发阈值。

选择最近任务后仍使用既有堆叠缩放和第二张卡片聚焦逻辑，并保留同一帧窗口旋转矩阵的横屏坐标修正。变化影响的是提前接管的时机；之前实测的横屏结果不能直接代替新包拖动阶段的设备回归。

## 验证与限制

扩展 `tools/test-launcher-entry-rotation.py`，执行生产 Java 的矩阵、缩放、滚动及目标切换方法。旧代码在“实时动画运行、最近任务待入场，但尚未提交 RECENTS”的矩阵保真用例失败。修改后共 670 项断言通过，涵盖原有 0/90/180/270 度窗口映射、多/单任务、带偏移和禁用旋转，以及向角落拖动、缩小、拖回、明确 RECENTS 后启用修正、改为非 RECENTS 后恢复原值及原厂样式隔离。

这些检查使用独立仿射变换和模拟 Android 状态，证明辅助方法不会再覆盖相应原厂输入，不等于已完成设备上整段小窗动画验收。本轮未检测到 ADB 手机，未安装新包，无法回读手机版本或声称实机通过。
